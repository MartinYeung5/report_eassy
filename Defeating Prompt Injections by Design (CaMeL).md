# Defeating Prompt Injections by Design (CaMeL) (2025) — In-Depth Paper Analysis

## Paper Highlights

CaMeL (Capabilities for Machine Learning), jointly proposed by Google DeepMind and ETH Zurich, is a system‑level defense framework for LLM agents. Its core idea is no longer to “teach” the model to recognise and resist prompt injections, but to architecturally ensure that prompt injections **cannot take effect in the first place** — by completely separating the control flow of trusted queries from the data flow of untrusted data, and by introducing a capability mechanism that enforces fine‑grained security policies on every tool call.

## Core Contributions

### Problem Definition

LLM agents are increasingly deployed in environments where they interact with untrusted sources — reading web pages, processing emails, manipulating cloud documents, etc. However, when an agent handles data from untrusted origins, attackers can embed malicious instructions into these data, tricking the agent into performing unauthorised actions or leaking sensitive information.

Existing defenses fall into two broad categories: prompt engineering (e.g., using delimiters to mark untrusted content, prompt sandwiching) and fine‑tuning the model for robustness. Yet both are fundamentally **heuristic** — they try to teach the model to “ignore” malicious instructions, but offer no security guarantees. Attackers can always find ways to bypass these heuristics.

Even the Dual‑LLM pattern proposed by Simon Willison (one privileged LLM for planning, one isolated LLM for handling untrusted data) protects the control flow (attackers cannot alter the sequence of tool calls), but the **data flow remains manipulable** — an attacker can poison the data so that the isolated LLM extracts attacker‑specified filenames and email addresses, leading to data exfiltration. The authors compare this to “parameter tampering” in SQL injection — the query structure is intact, but the parameters are swapped.

### Innovative Approach

CaMeL’s core innovation is to **systematically introduce proven security concepts from traditional software security** — Control‑Flow Integrity, Access Control, and Information‑Flow Control — into the domain of LLM agent security. Specifically:

**1. Explicit Extraction of Control and Data Flows**  
A **privileged LLM (P‑LLM)** first translates the user’s natural‑language query into restricted Python code. This code explicitly expresses the intended tool‑call sequence (control flow) and data dependencies (data flow). Crucially, the P‑LLM **only sees the user’s original query** and never accesses any data returned by tools.

**2. Isolated LLM for Structured Parsing Only**  
All data from untrusted sources (e.g., email bodies, document contents) are handed to an **isolated LLM (Q‑LLM)**. The Q‑LLM **has no tool‑calling capability** — it can only parse unstructured data into structured data according to predefined Pydantic schemas. It cannot invoke tools, send emails, or access file systems; even if fully controlled by a prompt injection, the damage it can cause is extremely limited.

**3. Capability Mechanism**  
This is CaMeL’s most refined security design. Each data value carries metadata tags (capabilities) recording its **provenance** and **allowed readers**. For example, a document read from cloud storage is tagged as “from cloud storage” and “readable only by a specific email list”. When the agent tries to invoke a tool (e.g., `send_email`), the CaMeL interpreter checks whether the tool’s arguments satisfy the security policy — if the document’s allowed readers do not include the recipient, the call is blocked.

**4. Custom Python Interpreter**  
CaMeL implements a custom Python interpreter that executes the code generated by the P‑LLM, maintains a data‑flow graph at runtime (tracking dependencies of each variable), and enforces security policies before every tool call. The interpreter uses a **restricted Python subset** to prevent dangerous operations.

### Research Results

The team evaluated CaMeL on the **AgentDojo** benchmark:

- **Provably secure task completion rate**: CaMeL achieved **77%** of tasks with provable security (i.e., no policy violations within CaMeL’s threat model).
- **No‑defense baseline**: The system without any defense achieved **84%** on the same tasks.
- **Utility cost**: CaMeL incurred about a **7‑percentage‑point** utility loss while providing provable security — a relatively mild cost given that the guarantee is **provable**, not probabilistic.

In addition, the paper formalises the **PI‑SEC security game**, turning the prompt‑injection defense problem into a formally verifiable security problem.

### Practical Deployment Potential

**High.** CaMeL’s advantage is that it **does not rely on the model’s own robustness** and can work with any LLM. The P‑LLM and Q‑LLM can be different models — the P‑LLM requires strong code‑generation capability (top‑tier models like GPT‑4 or Claude), while the Q‑LLM only needs structured parsing and can be smaller, faster, or even run locally. This design also offers a privacy benefit: model providers (e.g., OpenAI) only see the user’s original query and **never see sensitive data returned by tools**.

However, several practical issues remain: security policies require expert effort to write (though Python is more flexible than DSLs); error handling with untrusted data needs careful redaction; and the current version does not support transaction rollback.

## Technical Details

### Code Generation Example

The P‑LLM translates a natural‑language query into Python code. A typical example:

```python
email = get_emails(1)[0]
date = get_current_day()
if query_ai_assistant(
    "Is this email about a meeting on the day after {date}/\n{email}", 
    bool
):
    send_email(email.body, email.subject, "email@example.com")
```

This corresponds to the query: “If my last email is about tomorrow’s meeting, forward it to email@example.com.”

### Data‑Flow Graph Tracking

The CaMeL interpreter maintains a data‑dependency graph at runtime. In **STRICT mode**, even the condition itself is added as a dependency — meaning the `send_email` call depends not only on the email content but also on the result of `query_ai_assistant`, preventing information leakage through side channels.

### Security Policy Example

Below is a Python implementation of a policy for creating calendar events:

```python
def create_calendar_event_policy(
    self, tool_name: str, kwargs: Mapping[str, CaMeLValue]
) -> SecurityPolicyResult:
    participants: List[CaMeLStr] = kwargs["participants"]
    
    if is_trusted(participants):
        # If the participant list comes directly from a trusted source, allow the tool
        return Allowed()
    
    participants_set = set(participants.raw)
    if not can_readers_read_value(participants_set, kwargs["title"]):
        return Denied("The title is not public or shared with the recipients")
    # Similarly check description, location, start_time, end_time
    return Allowed()
```

The logic is straightforward: the event title, description, etc., must be readable by all participants; otherwise, creation is denied.

### Capability Annotations

Each value carries capabilities containing:
- **Provenance**: `User` (from user input), `CaMeL` (intermediate results from code execution), or a specific tool (e.g., `read_email`)
- **Allowed Readers**: `Public` (readable by everyone) or a set of user identifiers (e.g., email addresses)
- **Inner Source**: Tools can mark more granular provenance internally, e.g., `read_email` can tag the sender of the email.

## Experimental Setup

### Hardware & Software Configuration

- **Model selection**: In the paper, both P‑LLM and Q‑LLM use the same backbone (Gemini series in experiments), but the design allows different models.
- **Interpreter**: Custom interpreter built on Python’s `ast` library, running a restricted Python subset.
- **Benchmark**: AgentDojo (NeurIPS 2024), a dynamic agent security evaluation framework with multiple realistic scenarios (email, cloud storage, calendar, etc.).
- **Code open‑sourced**: https://github.com/google-research/camel-prompt-injection

### Design Constraints

- P‑LLM only sees the user query, never tool outputs.
- Q‑LLM has no tool‑calling privileges.
- P‑LLM is allowed at most 10 attempts to modify generated code.
- Error messages involving untrusted data are redacted before being passed to the P‑LLM.

## Comprehensive Analysis

**CaMeL represents a paradigm shift in LLM agent security research.** Most prior work attempts to “patch” the model — via better prompts, training data, or alignment — to make it safer. But this is essentially a cat‑and‑mouse game with a general‑purpose AI; attackers always find new jailbreaks.

CaMeL takes a fundamentally different path: **instead of trying to make the model secure, it makes the entire system secure at the architectural level.** This is analogous to parameterised queries for SQL injection in web security — rather than filtering malicious inputs, we eliminate the injection vector altogether.

The elegance of this approach lies in:

1. **Provable security**: not “probably secure”, but formally verifiable within the threat model.
2. **Model‑agnostic**: even if the underlying model is vulnerable or compromised, CaMeL’s security layer remains effective.
3. **Privacy enhancement**: model providers never see sensitive user data.

Of course, CaMeL has clear limitations:

- **It does not defend against pure text‑level attacks** — if an attack simply makes the LLM output a wrong summary (without involving tool calls or data exfiltration), CaMeL cannot prevent it.
- **Security policies require manual authoring** — though Python is more flexible than DSLs, it still needs security expert investment.
- **Utility cost**: the 77% vs 84% gap means about 7% of tasks are not completed under CaMeL.

Notably, CaMeL has been praised by some security researchers as “the first truly trustworthy prompt‑injection defense”. It has already gained attention in the open‑source community, with projects starting to integrate it into real‑world agent frameworks.

## Practical Recommendations

### Suitable Scenarios

1. **Enterprise LLM agents** handling sensitive data (financial documents, customer information, internal emails).
2. **Compliance‑required environments** needing auditability and provable data‑handling processes.
3. **Multi‑tenant agent systems** where data from different users must be strictly isolated.

### Deployment Suggestions

**1. Start with Security Policy Design**  
CaMeL’s effectiveness heavily depends on the quality of security policies. Begin by mapping out your business’s data flows and access‑control requirements, then define policies for the most critical tools (e.g., send email, access cloud storage).

**2. Choose the Right Model Combination**  
The P‑LLM needs strong code‑generation ability — if using open‑source models, consider CodeLlama or DeepSeek‑Coder. The Q‑LLM only needs structured output capabilities, so it can be smaller, faster, and even deployed locally to protect data privacy.

**3. Deploy Gradually**  
Start with low‑risk scenarios to accumulate policy‑writing experience. CaMeL’s Python policy functions are flexible, but careful design is needed to avoid introducing vulnerabilities in the policies themselves.

**4. Follow the Official Repository**  
The official codebase is open‑source, but the team acknowledges possible implementation bugs. Before production deployment, monitor community feedback and fixes closely.

**5. Combine with Human Approval**  
The paper explicitly states that CaMeL is not intended for fully autonomous systems. For high‑risk sensitive operations (e.g., sending emails containing confidential information), configure policies to require explicit user approval.
