# CaMeLs Can Use Computers Too: System-level Security for Computer Use Agents

## Paper Highlights

This paper addresses prompt injection attacks against Computer Use Agents (CUAs) by proposing a system‑level security solution based on architectural isolation. The core insight is that UI workflows, despite being dynamic, are structurally predictable – therefore a complete execution graph with conditional branches can be generated *before* any potentially malicious content is encountered, using “Single‑Shot Planning”. This provides provable control‑flow integrity without severely sacrificing performance. Experiments show that the approach preserves up to **57%** of frontier model performance while improving smaller open‑source models by as much as **19%**.

---

## Core Research Contributions

### Problem Definition

With the rapid advance of Vision‑Language Models (VLMs), Computer Use Agents (CUAs) can automate computer tasks just like humans – by observing screens, clicking, typing, etc. However, these agents face a critical security threat: **prompt injection attacks**. Attackers can embed malicious instructions in web pages, emails, documents, or any content the agent reads, hijacking the agent’s behaviour to steal credentials or cause financial loss.

The only known robust defence today is **architectural isolation** – strictly separating trusted task planning from untrusted environment observations. Applying this to CUAs creates a fundamental tension: existing agents must continuously observe the UI to decide each action, which directly conflicts with the isolation required for security. How to reconcile safety with the basic operating logic of CUAs is the core problem this paper tackles.

### Innovative Approach

The paper’s key insight is that **UI workflows are structurally predictable, even if they appear dynamic**. Based on this observation, the authors propose **Single‑Shot Planning**.

The framework consists of two critical components:

1. **Privileged Planner** – generates a complete execution graph with conditional branches *before* ever touching any potentially malicious UI content. This planner never accesses untrusted environment observations.

2. **Quarantined Perception** – executes the plan generated by the planner; it resolves concrete UI coordinates and values at runtime, but its execution paths are pre‑locked by the planner.

This design provides **provable control‑flow integrity guarantees** – no matter what malicious instructions an attacker injects into the UI, they cannot alter the agent’s predetermined execution path.

Moreover, the paper introduces a mechanism called **NOVA (Navigating via Observation, Verification, and Action)** to make single‑shot planning feasible in the combinatorially explosive UI state space.

Interestingly, the name “CaMeLs” is a double entendre – it’s a play on “camels” and also hints at “Computer‑use Agent Model with Enhanced/safe LLM”, echoing the humorous title that “camels can use computers too”.

### Research Results

Experiments are conducted on the **OSWorld** benchmark, with key results:

| Model Type | Performance |
|------------|-------------|
| Frontier Models | Preserve up to **57%** of performance |
| Smaller Open‑source Models | Improve by as much as **19%** |

These results demonstrate that strict system‑level security and practicality can coexist in CUAs.

More surprisingly, the study found that **half of the OSWorld tasks can be completed without the agent ever looking at the screen** – fundamentally challenging the conventional assumption that agents must continuously perceive the environment to operate effectively.

However, the paper also reveals an important security caveat: while architectural isolation successfully prevents instruction‑injection attacks, **branch‑steering attacks** remain a threat. In such attacks, adversaries manipulate UI elements to deceive the perception model, steering the execution down a legitimate but unintended branch – for example, redirecting the agent to a malicious website.

### Practical Deployment Potential

The application value is direct and immediate. As companies like Anthropic roll out computer‑use capabilities, CUAs are moving from labs to real enterprise and personal scenarios. The architectural isolation proposed here can serve as:

- **The security foundation for enterprise‑grade AI assistants**, preventing malicious emails, documents, or web content from hijacking automated workflows.
- **A security reference implementation for open‑source agent frameworks**, helping developers incorporate safety at the design stage.
- **Technical support for compliance and auditing** – provable control‑flow integrity provides a theoretical basis for security certification.

As the authors commented on Hugging Face: “When AI agents control your mouse, a malicious email can drain your account. We built the first system‑level defence to sandbox these agents.”

## Technical Details

### Dual‑LLM Architecture

The technical core can be summarised as a **Dual‑LLM Architecture**, with the following workflow:

```
┌─────────────────────────────────────────────────────────────────┐
│                       User Task Input                          │
│                   (e.g., “Clean up my inbox”)                  │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│                   Privileged Planner                           │
│  • Never touches untrusted UI content                          │
│  • Generates a complete conditional execution graph            │
│  • Example:                                                    │
│    IF unread emails in inbox → open first → check if spam      │
│    IF spam → move to trash                                     │
│    IF not spam → mark as read                                  │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│                 Quarantined Perception                         │
│  • Executes the plan issued by the planner                    │
│  • Resolves UI coordinates and values at runtime              │
│  • Cannot deviate from the predefined execution paths         │
└─────────────────────────────────────────────────────────────────┘
```

### Formalisation of Single‑Shot Planning

At a theoretical level, single‑shot planning can be formalised as:

Given a task goal *G*, the planner, without any UI observation, generates an execution graph *P = (V, E, C)*, where:

- *V* is a set of state nodes
- *E* is a set of action edges
- *C* is a set of conditional branches

The execution graph must satisfy: for any possible UI state *s* ∈ *S*, there exists exactly one valid path *p* ∈ *P* from the start node to a terminal node such that *p* accomplishes *G*.

This design ensures **control‑flow integrity** – attackers can only influence the evaluation of branch conditions (i.e., which predefined path is taken), but cannot introduce new execution paths.

### The NOVA Mechanism

NOVA (Navigating via Observation, Verification, and Action) is the key engineering mechanism that makes single‑shot planning practical. In a combinatorially explosive UI state space, the planner cannot enumerate all possible states in advance. NOVA addresses this via:

1. **Observation** – the perception module observes the current UI state at runtime.
2. **Verification** – matches the observation against the expected states in the plan.
3. **Action** – executes the corresponding predefined action based on the match result.

This design allows the planner to define only high‑level state categories and transition logic, while the perception module resolves concrete UI coordinates and details at runtime, drastically reducing planning complexity.

## Experimental Setup

### Benchmark

- **OSWorld** – a dedicated benchmark for evaluating computer‑use agents.
- **Task types** – cover a wide range of real‑world computer operations, including file management, email processing, web browsing, etc.

### Model Configurations

- **Frontier models** – several closed‑source frontier models were evaluated for performance retention.
- **Open‑source models** – several smaller open‑source models were evaluated for performance improvement.

### Attack Scenarios

- **Instruction‑injection attacks** – malicious instructions embedded in UI content to hijack agent behaviour.
- **Branch‑steering attacks** – manipulation of UI elements to trick the perception model into selecting an unintended but legitimate branch of the plan.

### Hardware Requirements

The paper does not specify detailed hardware requirements, but typical deployment for VLM inference (e.g., GPT‑4V, Claude‑scale models) would require:

- Sufficient GPU memory for running large VLMs.
- A stable system architecture for communication between the planner and perception modules.

## Comprehensive Analysis

### Theoretical Contribution

The theoretical value of this work lies in **redefining the security boundary for computer‑use agents**. Traditional agent security research focuses on detecting and filtering malicious inputs; this paper takes a more fundamental approach – rather than trying to identify all possible attacks, it architecturally constrains *what the agent can do*.

The philosophical basis is a rediscovery of *predictability*. The core claim – that UI workflows are structurally predictable despite being dynamic – seems simple but carries profound implications. It implies that many tasks previously thought to require real‑time perception can actually be planned ahead of time. The empirical finding that “half of OSWorld tasks can be completed without looking at the screen” strongly supports this theoretical stance.

### Security‑Performance Trade‑off

What is most impressive is the surprisingly favourable balance between security and practicality. **57% performance retention** for frontier models means most tasks still succeed; and for smaller open‑source models, the **19% improvement** reveals a counter‑intuitive fact: architectural isolation did not impair performance – on the contrary, structured planning helped smaller models complete tasks more effectively.

This “security as productivity” finding is a powerful rebuttal to those who fear that security measures inevitably drag down AI performance.

### Limitations and Open Challenges

The paper candidly acknowledges the remaining vulnerability – **branch‑steering attacks**. This is a noteworthy residual threat: although attackers cannot change the execution path, they can trick the perception model into choosing the “wrong” legitimate branch. For instance, a malicious website can masquerade as the legitimate site the user wants to visit, thereby luring the agent into a trap within the “visit website” branch.

This reveals a fundamental distinction between **control‑flow security** and **data‑flow security**: single‑shot planning guarantees the former, but the latter still depends on the accuracy of the perception model. This points to an important future direction – how to enhance the robustness of perception modules against adversarial manipulation without sacrificing practicality.

Moreover, as follow‑up work has noted, system‑level security for CUAs also involves long‑horizon constraint enforcement, secure permission binding, privacy‑preserving memory, and other open challenges. This paper lays a solid foundation for that subsequent research.

## Practical Recommendations

### For Developers

1. **Incorporate security at the architectural design stage** – don’t treat security as an afterthought. When designing a CUA system, prioritise the separation of planning and perception.

2. **Adopt “plan‑ahead” rather than “react‑in‑real‑time” thinking** – for tasks that can be structurally described, plan the complete workflow as much as possible in advance, reducing the agent’s decision‑making freedom when facing untrusted content.

3. **Pay attention to branch‑steering defences** – even with architectural isolation, test the adversarial robustness of the perception module against UI element manipulation.

### For Enterprises

1. **Prioritise architectural isolation in high‑risk scenarios** – for CUA applications involving financial operations or sensitive data access, adopt the proposed dual‑LLM architecture.

2. **Implement tiered security policies** – use different security configurations based on task risk levels: full single‑shot planning for high‑risk tasks, and moderate relaxation for lower‑risk tasks to gain performance.

3. **Monitor the open‑source ecosystem** – as more open‑source models benefit from architectural isolation, enterprises can consider using open‑source solutions instead of closed‑source models in security‑sensitive environments.
